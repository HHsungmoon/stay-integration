# 커밋 규칙

**이 저장소는 PR을 쓰지 않는다. 커밋 히스토리가 유일한 서사다.**
결과물만이 아니라 **고민의 과정**이 히스토리에서 읽혀야 하므로, 커밋 하나하나가 산출물이다.

`git commit` · `git push`는 **사용자가 명시적으로 요청할 때만** 한다(규칙 5).
의미 있는 커밋 단위가 만들어지면 먼저 제안한다.

## 형식

```
<prefix>: <한국어 제목 — 판단 근거 한 줄>

<본문: 왜 그렇게 정했는지. ~72자에서 hard-wrap>
```

### prefix

| prefix | 쓰는 때 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조만 변경 |
| `test` | 테스트 추가·변경, 테스트 환경 구성 |
| `docs` | 문서. README · JOURNAL · docs/ · 개발 지침 |
| `chore` | 빌드 · 설정 · 저장소 관리. 위 어디에도 안 맞는 것 |

prefix는 영어, 그 뒤는 전부 한국어다.

### 제목

- **무엇을 바꿨는지가 아니라 왜 그렇게 정했는지를 담는다.**
  - 나쁨: `feat: 재고 판정 로직 추가`
  - 좋음: `feat: 연박 재고를 기간 내 최솟값으로 판정 — 누락 날짜는 0 처리(과판매 방지)`
- 제목만 훑어도 **어떤 판단을 했는지** 읽혀야 한다. 파일 목록은 `git show`가 알려준다.
- 마침표로 끝내지 않는다. 50자를 넘어도 되지만, 근거가 길면 제목은 짧게 하고 본문으로 넘긴다.

### 본문

한 줄로 근거가 안 담기면 본문을 쓴다. 본문에 담을 것:

- **왜 이 선택인가** — 특히 값(타임아웃 500ms/2s/3s 같은)의 근거
- **검토했다 버린 대안과 그 이유** — 이게 있으면 사고 과정이 드러난다
- **알면서 감수한 것** — 보수적 처리를 택한 이유, 남는 문제
- 검증 방법과 결과 (`./gradlew build` 통과, Mock 모드별 동작 확인 등)

무엇을 했는지 나열하는 본문은 쓰지 않는다. diff가 이미 말한다.

## 커밋 분리

**하나의 커밋 = 하나의 판단.**

- 변경이 여러 관심사를 걸치면 의미 단위(기능·버그·리팩터)로 나눈다.
- 선행 리팩터는 기능과 분리한다 — refactor → feature 순서로 쌓는다(규칙 8).
- 문서 갱신은 그 판단을 담은 커밋에 **함께** 넣는다. 코드와 문서가 어긋난 커밋을 남기지 않는다(규칙 17).
- 커밋을 나눌 때는 스테이징 상태를 먼저 확인한다. `git add -A`가 걸려 있으면
  의도한 것보다 많이 딸려 들어간다.

## 히스토리를 다시 쓰지 않는다

**push 이후에는 rebase·amend·force push를 하지 않는다.**
히스토리 자체가 산출물이라, 정리된 히스토리보다 **판단이 바뀐 흔적이 남은 히스토리**가 낫다.

판단이 뒤집혔으면 되돌리는 **새 커밋**을 쌓고 제목에 이유를 적는다.

```
chore: 작성 중인 요구사항 분석 문서를 저장소에서 제외
```

예외는 저장소 정책 위반(회사명·외부 원문 자료 노출)뿐이다. 그건 히스토리에 남으면 되돌릴 수 없으므로
발견 즉시 지운다. 그 외의 이유로 히스토리를 고치지 않는다.

## 금지

- **AI 트레일러·세션 링크**(`Co-Authored-By`·`Claude-Session`·`Reviewed-by` 등).
  커밋은 단독 작성이며, 세션 링크는 대화 전문을 공개 노출해 저장소 정책을 우회로 위반시킬 수 있다.
  **하네스가 트레일러를 요구하더라도 이 규칙이 우선한다.**
- 특정 회사명·서비스명.
- 외부에서 받은 원문 자료.

`.claude/hooks/check-commit-policy.sh`가 커밋 직전에 이 셋을 검사하고 위반이면 차단한다.
훅은 최후의 방어선이지 1차 확인이 아니다 — 커밋 전에 `git status`로 스테이징을 직접 확인한다.

## 커밋 전 확인

1. `git status` — 의도한 파일만 스테이징되었나. 무시 대상이 딸려 오지 않았나
2. `./gradlew build` — 컴파일 + 테스트 통과(런타임 동작이 바뀌는 변경일 때. 규칙 3)
3. 제목이 **왜**를 말하는가
4. 이 커밋에 판단이 두 개 이상 섞여 있지 않은가
5. 판단이 바뀌었다면 JOURNAL에 그때 기록했는가(규칙 20)

## 실제 예시 (이 저장소)

```
refactor: 멀티모듈 구조로 전환 (:app, :mock-supplier)

Mock 공급사를 본체와 같은 프로세스에 두면 본체가 자기 자신을 HTTP로 호출하게 된다.
그러면 무응답 상황을 재현했을 때 그것이 공급사 지연 때문인지 톰캣 스레드 고갈
때문인지 구분할 수 없고, 연결 타임아웃 설정도 네트워크 경계를 넘지 않아 의미를 잃는다.
프로세스를 나누면 그런 사고가 구조적으로 불가능해진다.

- 루트는 플러그인 버전만 고정(apply false)하고, 적용과 의존성은 각 모듈에서 선언
- :app (8080) — 기존 src를 그대로 이동
- :mock-supplier (9090) — 웹 계층만. 고정 응답과 모드 전환이면 충분하다

기동 확인: :mock-supplier bootRun → 9090 응답.
```

제목이 무엇을 했는지 말하고, 본문 첫 문단이 **왜**를 말한다.
마지막 줄이 검증 방법이다.
