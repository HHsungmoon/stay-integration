# Mock 공급사 서버 규칙

본체(`:app`)와 **별도 프로세스**로 뜬다(9090). 같은 프로세스에 두면 본체가 자기 자신을 HTTP로
호출하게 되어, 무응답을 재현했을 때 공급사 지연인지 톰캣 스레드 고갈인지 구분할 수 없다.

## 재현할 수 있어야 하는 것 3가지

이 셋이 있어야 타임아웃과 부분 실패가 실제로 동작함을 보일 수 있다.

| 모드 | 동작 |
|---|---|
| `normal` | 정상 응답 |
| `error` | 공급사 장애 |
| `no-response` | 무응답 (응답을 주지 않고 붙잡고 있는다) |

## 장애 표현은 공급사마다 다르게 만든다

한쪽은 HTTP 5xx, 다른 쪽은 **HTTP 200 + 본문 실패 코드**.

둘을 똑같이 만들면 "실패 판정 통일"을 증명할 수 없다 — **Mock이 문제를 감춰버린다.**

## 그 외

- 모드는 런타임에 바꾼다(제어 엔드포인트). 공급사별로 따로 걸 수 있어야 한다.
- 숙소 목록 API에도 장애를 걸 수 있으면 동기화 실패 경로(D-8)를 검증할 수 있다.
- 제공할 API는 2단계다 — ① 숙소 목록(조건 파라미터 없음) ② 재고·요금(숙소 코드 목록 bulk, 최대 50개).
- 요청 파라미터를 무시하고 고정 응답을 줘도 된다.

**코드 품질은 보지 않는다. 데이터 다양성에 시간을 쓰지 않는다.**
여기는 본체가 아니라 본체를 검증하기 위한 도구다.
