## 2. 문제 요구사항

### 2.1 배경 (해석)

숙박 플랫폼은 직접 등록한 숙소 외에 **외부 공급사(Supplier)의 상품을 연동해 함께 판매**한다.
문제는 공급사마다 API 표현이 다르다는 점이다. 같은 객실을 두고도 요금 단위, 세금 포함 여부, 실패 표현 방식이 제각각이다.
고객은 상품이 어느 공급사에서 왔는지와 무관하게 **동일한 형태의 검색 결과**를 봐야 한다.

따라서 이 시스템의 본질은 **"서로 다른 표현을 하나의 표준 모델로 흡수하고, 외부 실패를 전제로 안정적으로 응답하는 연동 계층"**이다.

### 2.2 필수 구현 (6개)

| # | 항목 | 한 줄 요약 |
|---|---|---|
| ① | 통합 모델 설계 | 공급사 A·B의 표현을 흡수하는 자사 표준 숙박 상품 모델 정의. 무엇을 버리는지 알고 선택 |
| ② | 공급사 연동 어댑터 | WebClient로 각 공급사를 호출하고 표준 모델로 변환. 공급사 형식이 도메인으로 새지 않게 경계 |
| ③ | 통합 검색 API | 검색 요청 1건 → 여러 공급사 병렬 조회 → 정규화·병합 → 응답 |
| ④ | 연동 견고성 | 병렬 호출 / 타임아웃 / 부분 실패 허용 / 실패 판정 통일 |
| ⑤ | Mock 공급사 | 정상·장애·무응답 3가지 상황 재현 가능 |
| ⑥ | 설계 근거 문서 | README에 빌드·실행 방법과 설계 의사결정. 문서 내용이 코드에 실제로 반영되어야 함 |

### 2.3 선택 구현 (설계 문서로 대체 예정 → 결과는 오른쪽)

| 항목 | 결과 |
|---|---|
| 재시도 정책 (무엇을 재시도하고 무엇을 하지 않을지, 백오프) | **안 함** — 데드라인 3s 안에 예산이 없다. `FailureKind.retryable()`만 남겼다(`05` §13) |
| 서킷 브레이커 (반복 실패 공급사 차단과 복구) | **구현** — Resilience4j, 공급사당 하나(`07`) |
| 요금/재고 캐시 (TTL, 스탬피드 방지, 정합성 오차 허용 범위) | **안 함** — 총액이 검색 조건 종속값, 재고는 호출마다 바뀐다(`06` 미구현 항목) |

| 통화 처리 | **안 함** — 정책 문제. 단일 통화(`05`) |
| 예약 대행 흐름과 보상 처리 | **설계만** — `09` |

## 3. 요구사항 구체화

### 3.1 두 공급사의 차이 (해석 정리)

두 공급사 모두 **숙소 > 객실 타입** 2단계 구조이며, 요금·재고는 객실 타입 단위다. 개별 물리 객실은 노출하지 않는다.

| 관점 | 공급사 A | 공급사 B |
|---|---|---|
| 숙소 식별자 | `hotelCode` (공급사 내 유일) | `propertyId` (공급사 내 유일) |
| 객실 타입 식별자 | `roomTypeCode` (**해당 숙소 안에서만** 유일) | `roomId` (**해당 숙소 안에서만** 유일, 이름과 달리 물리 객실 아님) |
| 요금 단위 | 날짜별 1박 단가 배열 | 숙박 기간 전체 총액 1개 |
| 세금 | 별도(net). 날짜별 세금액 분리 제공 | 포함(gross). 세금액 미제공, 포함 여부 플래그만 |
| 재고 | 날짜별 잔여 객실 수 | 날짜별 잔여 객실 수 |
| 조식 포함 | 재고·요금 응답에만 있음 | 재고·요금 응답에만 있음 |
| 실패 표현 | HTTP 4xx/5xx + 본문 에러 코드 | **항상 HTTP 200** + 본문 `resultCode` (`"0000"`만 성공, 실패 시 `data`는 null) |
| 응답 래핑 | 최상위 `items[]` | `data.items[]` |
| 통화 | ISO 4217 코드, 최소 단위 정수 | 동일 |

공통 규약:
- 인증: `X-Api-Key` 헤더
- 날짜: `YYYY-MM-DD`, 체크아웃일은 숙박일에 포함되지 않음 (9/1 in, 9/4 out = 3박)
- 인원: `adults`, `children` 분리 요청. `maxOccupancy`는 합산 기준
- 공급사는 요청 인원을 수용 가능한 객실 타입만 반환

두 공급사 모두 **API가 두 단계로 나뉜다** (중요):

| 단계 | 성격 | 특징 |
|---|---|---|
| ① 숙소 목록 | 정적 콘텐츠 | 조건 파라미터 없음. 요금·재고 없음. 자주 안 바뀜 |
| ② 재고·요금 조회 | 동적 데이터 | **숙소 코드 목록을 받아** bulk 조회. 한 번에 최대 50개. 호출마다 값이 달라짐 |

즉 공급사는 "지역으로 검색"해 주지 않는다. **어떤 숙소를 물어볼지 우리가 먼저 알고 있어야** 하고, 그 목록의 출처가 ①이다.

### 3.2 통합 모델 설계

#### 3.2.1 엔티티 단위

- **숙소(Property)**: 내부 식별자, 숙소명
- **객실 타입(RoomType)**: 내부 식별자, 객실 타입명, 최대 수용 인원, 소속 숙소
- **요금·재고 제안(Offer)**: 검색 시점의 조회 결과. **DB에 저장하지 않음**. 출처 공급사, 대상 객실 타입, 요금, 예약 가능 객실 수, 조식 포함 여부, 통화

#### 3.2.2 요금 모델 (확정 — 이 프로젝트의 핵심 판단)

A는 날짜별 단가에서 총액을 계산할 수 있지만, B는 총액만 주므로 날짜별 단가를 **만들 수 없다**.
총액을 숙박일수로 나누는 것은 존재하지 않는 값을 지어내는 것이므로 배제한다.

따라서 두 공급사가 **모두** 채울 수 있는 공통 분모는 `"숙박 기간 전체 총액, 세금 포함(gross)"` 하나다.

- A → `Σ (nightlyRate + taxAmount)` 로 상향 정규화 (net → gross)
- B → `totalPrice` 그대로 (이미 gross)

**확정: 공통 계약 + 선택적 확장의 2계층 구조**

| 계층 | 필드 | 채우는 주체 |
|---|---|---|
| `price` (필수) | `currency`, `totalAmount`(gross·기간 전체), `taxIncluded`, `breakfastIncluded`, `nights` | 모든 공급사가 **반드시** 채운다 |
| `priceDetail` (nullable) | `taxAmount`, `nightlyBreakdown[]` | 제공 가능한 공급사만. B는 `null` |

`(a) 공통 분모만 남기고 A의 날짜별 내역을 버린다`를 먼저 검토했으나 뒤집었다.
어댑터가 이미 파싱해 둔 값이라 **추가 비용이 사실상 0인데**, 버리면 A가 가진 정보를 시스템 전체에서 영구히 잃는다.
통합 계층의 목적은 "공통 분모로 하향평준화"가 아니라 **"모두가 지키는 계약 위에 공급사별 정보를 선택적으로 얹는 것"**이다.
nullable임이 계약에 명시되어 있으면 응답 일관성도 깨지지 않는다.

**잃는 것 / 감수하는 위험** (명시적으로 기록한다)

- B에서는 날짜별 요금 내역과 세금 금액을 **알 수 없고, 앞으로도 알 수 없다.** 추정하지 않는다.
- 클라이언트가 `priceDetail`에 의존해 로직을 짜면 **공급사 종속이 응답 계약을 타고 새어 나간다.**
  → 스키마에 nullable임을 명시하고, 정렬·필터·비교 등 **의사결정 로직은 `price`만으로 가능해야 한다**는 것을 계약 조건으로 못 박는다.
- `nightlyBreakdown`의 `net`/`tax`는 A의 원본 표현이다. A는 총액 필드를 주지 않으므로 `price.totalAmount`는 이 내역을 합산해 **우리가 만드는 값**이다 —
  따라서 "합계와 총액이 일치하는지"는 검증이 아니라 항등식이다. 어댑터가 실제로 잡는 결함은 음수 요금·세금, 통화 누락, 날짜 형식 오류이며,
  해당 **항목만** 제외하고 나머지 상품은 살린다(2026-09-05 정정. 상세는 `05-adapter.md` §5.4).

**`totalAmount`는 상품의 고유 속성이 아니라 검색 조건 종속값이다** (중요)

B의 `totalPrice`는 "요청한 숙박 기간 전체의 총액"이다. 즉 표준 총액은 `(checkIn, checkOut, adults, children)`에 종속된 값이며,
- 부분 기간으로 다시 쪼개 계산하는 것이 B에서는 **불가능**하고,
- 캐시를 도입한다면 **캐시 키에 검색 조건 4개가 전부 들어가야 한다** (§3.3 선택 구현 캐시 전략의 전제).

**1박 평균 단가는 제공하지 않는다.** `totalAmount / nights`는 계산 가능하지만, 고객이 이를 A의 실제 날짜별 단가로 오해할 수 있다.
대신 `nights`를 응답에 담아 필요한 쪽이 직접 계산하게 한다.

#### 3.2.3 조식 포함 여부는 요금(Offer)의 속성

같은 객실 타입이라도 공급사마다 조식 포함 여부가 다를 수 있고, 숙소 목록 API에는 이 정보가 없다.
→ 객실 타입의 속성이 아니라 **Offer의 속성**으로 둔다. 이 구분을 놓치면 "같은 객실인데 가격이 다르다"는 잘못된 비교가 생긴다.

#### 3.2.4 DB 저장 대상 — 식별자 매핑만

요금·재고의 원본은 외부에 있으므로 쌓지 않는다. 저장하는 것은 **공급사 코드 ↔ 내부 식별자 매핑**뿐이다.

| 매핑 | 공급사 쪽 키 (유니크) | 내부 |
|---|---|---|
| 숙소 | `(supplier, supplierHotelCode)` | 내부 숙소 ID |
| 객실 타입 | `(supplier, supplierHotelCode, supplierRoomTypeCode)` | 내부 객실 타입 ID |

객실 타입 코드는 숙소 안에서만 유일하므로 **매핑 키에 숙소 코드가 반드시 포함**되어야 한다.

불변 조건:
- 같은 공급사 상품이 다시 조회되면 **항상 같은 내부 식별자**가 나와야 한다 (멱등성). 동기화를 여러 번 돌려도 ID가 바뀌면 안 된다 → 유니크 제약 + upsert.
- 공급사가 다르면 내부 식별자도 달라도 된다. A의 어떤 숙소와 B의 어떤 숙소가 실제로 같은 곳이라도 기본 동작은 **따로 식별**한다. 병합은 선택 구현.
- **공급사 목록에서 사라진 상품은 하드 삭제하지 않는다.** `active` 플래그로 비활성화(soft delete)한다.
  삭제 후 재등장하면 새 내부 식별자가 발급되어 위 멱등성 불변 조건이 깨지기 때문이다.
  비활성 상품은 검색 대상(공급사에 물어볼 코드 목록)에서만 제외한다.
- 매핑 레코드는 `supplierHotelName` / `supplierRoomTypeName`을 함께 보관한다. 동기화 시점의 스냅샷이며,
  검색 응답의 이름은 재고·요금 응답 값을 우선한다(§3.5).

### 3.3 매핑 동기화 시점 (확정)

숙소 목록(정적)과 재고·요금(동적)의 성격 차이를 설계에 반영해야 한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 앱 기동 시 1회 | 단순 | 기동 중 공급사 장애 시 매핑이 비거나 앱이 안 뜸 |
| 주기적 스케줄 | 변경 자동 반영 | 하루 예산에서 스케줄러 인프라 추가 |
| 별도 명령(관리 엔드포인트/CLI) | 명시적, 재실행 가능 | 수동 |

**확정: 기동 시 1회 시도 + 관리 엔드포인트로 재실행 가능.** 주기적 스케줄은 설계 문서로만 남긴다.

근거 — 숙소 목록은 **정적 콘텐츠**이고 재고·요금은 **매 호출마다 달라지는 동적 데이터**다.
정적인 쪽을 매 검색마다 조회하면 고객 응답 경로에 불필요한 외부 호출이 2번 더 붙고, 그 호출의 장애가 검색 전체를 막는다.
따라서 정적 데이터는 **고객 요청 경로 밖에서** 미리 확보해 DB에 두고, 검색은 DB만 읽는다.
운영에서는 여기에 일 1회 스케줄을 얹으면 되며, 그 자리를 관리 엔드포인트가 대신한다.

**매핑 단계가 실패하면?** 앱은 정상 기동하고, 기존 DB 매핑으로 서비스한다. 매핑이 아예 없으면 검색 결과가 비지만 이는 장애가 아니라 "동기화 전 상태"이며 로그로 드러나야 한다. 공급사 하나의 목록 조회 실패가 다른 공급사 동기화를 막아서는 안 된다.

### 3.4 공급사 어댑터 경계

- 도메인 계층은 공급사 A·B의 필드명, 래핑 구조, 실패 표현 방식을 **전혀 모른다**.
- 공통 포트(인터페이스): `숙소 목록 조회()`, `재고·요금 조회(숙소 코드 목록, 기간, 인원)`. 반환은 표준 모델 또는 공통 실패 타입.
- 공급사별 어댑터가 (1) WebClient 호출 (2) 응답 DTO 역직렬화 (3) 실패 판정 (4) 표준 모델 변환을 모두 자기 안에서 끝낸다.
- 공급사 DTO 클래스는 어댑터 패키지 밖으로 나가지 않는다.
- **신규 공급사 추가 시 고칠 것**: 어댑터 구현체 1개 + 설정(엔드포인트/키) + 레지스트리 등록. 도메인·검색 서비스·응답 모델은 무변경. 이 사실을 문서에 명시.

### 3.5 통합 검색 흐름

```
[사전] 공급사 숙소 목록 조회 → 내부 숙소·객실 타입으로 매핑해 저장

고객 검색 요청 (체크인, 체크아웃, 성인, 아동)
  → 요청 검증 (체크아웃 > 체크인, 인원 ≥ 1 등)
  → DB 매핑에서 보유 숙소를 공급사별 코드로 묶음 (50개 단위 청크)
  → 공급사별 청크를 병렬 조회 (WebClient)
  → 각 응답을 표준 모델로 정규화 (어댑터)
  → 연박 재고 판정 (§3.6)
  → 병합 — 한쪽이 실패해도 나머지로 응답, 실패 사실 포함
  → 통합 검색 결과 반환
```

응답에 반드시 담을 것:
- 내부 숙소 식별자·숙소명
- 내부 객실 타입 식별자·객실 타입명
- 최대 수용 인원 (1실 기준)
- 예약 가능 객실 수 (요청 기간 전체 기준. 0이면 예약 불가)
- 출처 공급사
- 요금 (§3.2.2 기준으로 직접 설계)
- 부분 실패 사실 (어느 공급사가 실패했는지)

**요청 검증** (공급사에 잘못된 요청을 흘리지 않기 위해 우리 쪽에서 먼저 막는다)

| 규칙 | 처리 |
|---|---|
| `checkOut > checkIn` | 위반 시 400 |
| `adults >= 1`, `children >= 0` | 위반 시 400 |
| 최대 숙박일수 상한 (30박) | 초과 시 400. 상한이 없으면 응답 크기와 공급사 부하가 무제한이 된다 |
| **과거 체크인 날짜** | **거부하지 않는다** |

과거 날짜를 거부하지 않는 이유: 공급사가 어차피 재고 0 또는 빈 결과를 주므로 우리가 막을 실익이 없고,
막으면 "오늘"에 따라 동일 요청의 성패가 갈려 **테스트·문서 예시가 시간이 지나면 깨진다.**
(실제로 스펙 예시의 `checkIn=2026-09-01`은 이미 과거 날짜다.) → **구현: 예시 날짜를 고정값 그대로 쓴다.** 과거 날짜를 거부하지 않으므로 고정 예시가
시간이 지나도 깨지지 않는다 — 상대 날짜 표기는 필요가 없어졌다.

**매핑에 없는 상품이 재고·요금 응답에 온 경우**

카탈로그 동기화 이후 공급사가 객실 타입을 추가하면, 재고·요금 응답에 **내부 식별자가 없는 상품**이 섞여 온다.
최소 계약이 내부 식별자를 요구하므로 응답에 담을 수 없다.

- 처리: **해당 항목만 제외 + 경고 로그 + 카운터 증가.** 전체 응답을 실패시키지 않는다.
- 이것이 선택 구현 "정규화 실패 격리"의 최소 버전이다. 카운터가 0이 아니면 동기화가 밀렸다는 신호다.

**최대 수용 인원의 신뢰 출처**

`maxOccupancy`는 숙소 목록(①)과 재고·요금(②) 양쪽에 있다.
검색 응답에는 **②의 값**을 쓴다(요청 시점 기준으로 더 최신). ①의 값은 매핑 생성용이며, 두 값이 다르면 로그로 남긴다.
숙소명·객실 타입명도 같은 원칙을 따른다.

**50개 초과 시 (숙소가 수천 개일 때)** — 확정: 청크 분할과 동시성 제한을 **둘 다 구현**한다

- 공급사별 코드를 50개 청크로 나눠 fan-out
- 청크 단위 부분 실패 허용 (청크 하나의 실패가 전체를 죽이지 않음)
- **동시 실행 수 제한** — 무제한 병렬은 공급사 rate limit(429)을 자초한다. 공급사별 동시성 상한을 두고 초과분은 대기.
  Reactor `flatMap(fn, concurrency)`의 인자 하나이므로 구현 비용이 사실상 0이고, "문서에 적은 내용이 코드에 반영되어야 한다"는 요구에 직접 부합한다.
- **남는 문제(설계 문서 항목)**: 청크가 수십 개면 동시성 상한 때문에 라운드가 여러 번 돌아 §3.7의 전체 데드라인을 초과할 수 있다.
  이때는 데드라인 도달 시점까지 완료된 청크만으로 응답하고, 미완료 청크를 부분 실패로 표시한다. 즉 **"전부 아니면 무"가 아니라 시간 예산 내 최선"**.
  → **구현됨**(`06` §4 B — `take(deadline)` + 안 온 청크 수만큼 `TIMEOUT` 보정). 300숙소·6청크·지연 1s로 실제 와이어에서 확인(`06` §13).

### 3.6 연박 재고 판정 (확정)

재고는 날짜별로 온다. N박을 예약하려면 N일 모두 그 객실 타입이 남아 있어야 한다.

- **예약 가능 객실 수 = 요청 기간 내 날짜별 `remainingRooms`의 최솟값**
- 어느 하루라도 0이면 전체가 0 (예약 불가)
- **응답에 요청 날짜 중 일부가 누락되면 → 해당 날짜를 0으로 간주** (보수적). 팔 수 없는 상품을 파는 것보다 못 파는 것이 낫다.
- 응답에 요청 범위 밖 날짜가 섞여 오면 무시

**예약 불가 상품(0)을 응답에서 뺄지, 0으로 노출할지** — 확정: 0으로 노출:
- 뺀다 → 응답이 깔끔, 고객이 볼 상품만 보임
- 0으로 노출 → "매진"을 보여줄 수 있음, 클라이언트가 판단
- 확정: **0으로 노출 + `available: false` 불리언 병기.** 정렬·페이징이 비범위인 상황에서 필터링을 서버가 강제할 이유가 없고, "매진"은 그 자체로 의미 있는 정보다.
- `remainingRooms`가 음수로 오면 0으로 clamp한다 (스펙상 없어야 하지만 방어).
- 남는 문제(설계 문서 항목): 숙소가 수천 개가 되면 매진 상품까지 전부 내려보내 응답이 비대해진다.
  실운영에서는 `includeSoldOut` 쿼리 파라미터로 클라이언트가 고르게 하고 기본값을 `false`로 둔다.

### 3.7 연동 견고성 (필수 4가지)

#### 병렬 호출 — 실패를 예외가 아니라 **값**으로 다룬다

공급사 A·B(및 청크)를 동시에 던지고 모은다. 순차 호출은 지연이 합산되므로 배제.

구현의 핵심은 병렬화 자체가 아니라 **실패의 표현 방식**이다.
실패를 예외로 전파하면 스트림 하나가 죽을 때 전체가 죽어 **부분 실패 허용이 구조적으로 불가능**해진다.
따라서 각 호출의 결과를 성공/실패를 모두 담는 값 타입(`SupplierResult`)으로 변환한 뒤 합친다.

```
Flux.fromIterable(calls)                          // (공급사 × 50개 청크) 단위
    .flatMap(call -> adapter.fetch(call)
                       .map(SupplierResult::success)
                       .onErrorResume(e ->        // 예외를 값으로 강등
                           Mono.just(SupplierResult.failure(call.supplier(), classify(e)))),
             CONCURRENCY)                          // 공급사별 동시 실행 상한
    .collectList()
    .timeout(ORCHESTRATION_DEADLINE)               // §3.7 3계층 중 최상위
    .block();                                      // 톰캣 워커 스레드에서 단 한 번
```

→ 구현은 데드라인을 병합 스트림 전체가 아니라 **공급사 단위**로 건다(`take(deadline)`) — 전체에 걸면 하나가 늦을 때 먼저 온 공급사 결과까지 잃는다(`06` §2·§4).
어댑터가 실패를 값으로 돌려주므로 `onErrorResume`은 계약 위반 안전망일 뿐이다.

이 구조의 부수 효과가 중요하다.
- B의 `resultCode` 실패도 어댑터 안에서 같은 `SupplierResult.failure`로 변환되므로, **"실패 판정 통일"이 별도 장치 없이 달성**된다.
- `SupplierResult`가 이미 공급사·소요시간·결과 분류를 들고 있으므로, **관측성 지표가 사실상 공짜로 나온다** (§4.8).

#### 스레드 모델 — MVC 위에서 WebClient를 쓸 때의 함정 (필독)

MVC(블로킹)와 WebClient(논블로킹)를 섞을 때 가장 흔한 사고는 **Netty 이벤트 루프 스레드에서 블로킹 호출을 하는 것**이다.
이벤트 루프는 소수(코어 수)뿐이라 하나만 막혀도 그 위의 모든 외부 호출이 함께 멈춘다.
스펙이 경고한 "Mock을 같은 포트에 두지 마라"와 정확히 같은 종류의 사고다.

지켜야 할 규칙:

1. **JPA 조회(블로킹)는 reactive 체인에 들어가기 전에 전부 끝낸다.**
   매핑 조회는 검색 시작 시점에 한 번에 읽어 `Map<(supplier, hotelCode, roomTypeCode) → 내부 식별자>` 형태의 in-memory 자료구조로 만든 뒤 체인에 넘긴다.
   체인 안에서 `repository.findBy...`를 호출하는 코드는 금지한다.
2. **`.block()`은 컨트롤러 경계에서 단 한 번**, 톰캣 워커 스레드 위에서만 호출한다. 체인 중간의 `block()`은 금지.
3. 정규화는 순수 함수로 유지한다 (외부 I/O·DB 접근 없음). 그래야 어느 스레드에서 실행되든 안전하고 단위 테스트가 쉽다.

이것이 "WebFlux 전면 도입 없이 MVC 위에서 WebClient만 쓴다"는 선택의 실질적인 내용이다.
WebClient는 **외부 호출의 병렬화·타임아웃 제어 도구로만** 쓰고, 애플리케이션의 나머지는 블로킹 스택 그대로 둔다.

#### 타임아웃 (확정 — 3계층)

타임아웃은 두 개가 아니라 **세 개**다. 세 번째가 없으면 "왜 그 값인가"에 대한 설명이 완결되지 않는다.

| 계층 | 값 | 근거 |
|---|---|---|
| 연결 (TCP connect) | **500ms** | 같은 네트워크 대역의 정상 연결은 수십 ms. 500ms를 넘으면 회복이 아니라 대기일 뿐 |
| 응답 (호출 1건의 read) | **2s** | 검색 전체 목표 3s에서 병합·직렬화 여유를 뺀 값. 공급사 1건이 2s를 넘으면 그 결과를 기다리는 것보다 부분 실패로 응답하는 편이 고객 경험상 낫다 |
| **오케스트레이션 데드라인 (검색 전체)** | **3s** | 청크가 여러 개이거나 재시도가 붙으면 개별 응답 타임아웃의 **합이 전체 목표를 초과**한다. 병합된 스트림 전체에 한 번 더 건다 |

- 값의 출발점은 임의의 숫자가 아니라 **"고객 검색 응답 목표 3초"** 이고, 거기서 아래로 역산했다.
- 세 값 모두 YAML 설정으로 빼고 근거를 주석으로 남긴다. 공급사별로 다른 값을 줄 수 있게 공급사 단위 설정으로 둔다.
- 재시도(선택 구현)를 켜면 **최악의 경우 소요 시간 = (응답 타임아웃 × 시도 횟수)** 가 되어 데드라인을 넘길 수 있다.
  따라서 재시도 총 예산도 데드라인 안에 들어오도록 제한한다.

#### 부분 실패 허용
- 한 공급사가 타임아웃/장애여도 나머지 결과로 응답한다.
- 실패한 공급사는 응답에 명시한다 (예: `failedSuppliers: ["A"]` 또는 공급사별 상태 목록). 조용히 감추지 않는다.
- **모든 공급사가 실패하면?** 확정: **HTTP 200 + 실패 목록 + 상태 필드.**
  "결과 없음(정상 조회했으나 상품 없음)"과 "조회 불가(전부 실패)"는 다른 사건이므로 클라이언트가 구분할 수 있어야 한다.
  응답 본문에 `status: OK | PARTIAL | ALL_FAILED` 를 둔다.
  - 검토했으나 택하지 않은 대안: 전부 실패 시 503. 상태 코드로 알리면 명확하지만, 일부 성공(PARTIAL)과 전부 실패를 **다른 성공/실패 축으로 나누게 되어** 클라이언트가 두 가지 판정 로직을 갖게 된다. 한 축(본문 상태 필드)으로 통일하는 편이 낫다고 판단.
  - 다만 200으로 응답하면 **중간 캐시·CDN이 빈 결과를 정상 응답으로 캐싱**할 위험이 있으므로, `ALL_FAILED`/`PARTIAL` 응답에는 `Cache-Control: no-store`를 붙인다.

#### 실패 판정 통일
- B는 장애 시에도 HTTP 200을 준다. **본문 `resultCode`를 확인하지 않으면 장애가 "빈 결과"로 둔갑**한다.
- 각 어댑터가 자기 공급사의 실패 표현을 **공통 실패 타입**으로 번역한다. 도메인/검색 서비스는 "실패했다"는 사실과 분류만 알면 된다.
- 실패 분류 (선택 구현인 재시도 정책의 기반이 되므로 지금 정의):
  - **일시적(재시도 가치 있음)**: 타임아웃, 5xx, 일시적 장애(503/E503), 호출 한도 초과(429/E429)
  - **영구적(재시도 무의미)**: 인증 실패(401/E401), 잘못된 요청(400/E400), 코드 50개 초과
  - **정규화 실패**: 응답은 왔으나 표준 모델로 변환 불가
  - → **구현: 3분류가 아니라 원인 8값 `FailureKind` + `retryable()`.** 로그·지표에서 "왜 실패했나"를 읽으려면 원인이 필요했다(`05` §3). 같은 술어가 서킷의 기록 기준이다(`07` §2)

#### MVC + WebClient 조합 이유 (요약)
- WebFlux 전면 도입은 요구되지 않으며, 검색 외 흐름(매핑 저장 등)은 JPA 기반이라 블로킹 스택이 자연스럽다.
- WebClient는 외부 호출의 병렬화·타임아웃 제어 도구로만 쓰고, 컨트롤러 경계에서 결과를 모아 동기 응답한다.
- 지켜야 할 구체적 규칙은 위 "스레드 모델" 항목에 있다. 이 규칙을 안 지키면 MVC+WebClient 조합은 이득 없이 위험만 남는다.

### 3.8 Mock 공급사

- 재현 필수: **정상 / 공급사 장애 / 무응답** 3가지. 선택: 응답 지연(N초 후 정상)
- 장애 표현은 공급사별로 다르게: A는 HTTP 503, B는 HTTP 200 + 실패 코드
- 제어 방식: 런타임에 모드를 바꾸는 제어 엔드포인트 (`normal | error | no-response`)
- 요청 파라미터는 무시하고 고정 응답을 줘도 됨. **코드 품질·데이터 다양성에 시간을 쓰지 않는다.**
  → **구현: 요청 기간에 맞춰 날짜별 값을 생성한다.** 고정 응답이면 우리 재고 규칙(누락 날짜 = 0)이 정확히 작동해 정상 케이스가 전부 매진이 된다(`03` §2.1).
  데이터 다양성에는 시간을 쓰지 않았고, 규모 테스트용 합성 숙소만 나중에 붙였다(`03` §10)
- 숙소 목록 API에도 장애 모드를 걸 수 있게 해 두면 §3.3의 "매핑 실패" 시나리오를 검증할 수 있다 (여유 있으면) → **구현**(모드가 공급사 × API 단위)

### 3.9 테스트 전략

- 단위: 정규화 로직 (A 총액 계산, B 통과), 연박 재고 최솟값 판정, 누락 날짜 처리, B `resultCode` 실패 판정
- 통합: Mock 모드를 바꿔가며 (1) 정상 병합 (2) A 무응답 → B만으로 응답 + 실패 표시 (3) B 장애(200+E503) → 실패로 인식 (4) 둘 다 실패
- 견고성은 "구현했다"가 아니라 **테스트로 증명**한다.

## 4. 기능 명세

엔드포인트·필드 상세는 설계 단계에서 정한다. 여기서는 각 기능의 **역할과 책임**만 정의한다.

### 4.1 공급사 카탈로그 동기화
공급사의 숙소 목록 API를 호출해 숙소·객실 타입 목록을 가져오고, 내부 식별자 매핑으로 저장한다.
이미 존재하는 매핑은 유지(멱등), 새 상품은 신규 식별자 발급. 공급사 하나의 실패가 다른 공급사 동기화를 막지 않는다.
기동 시 자동 실행되며, 수동으로 다시 실행할 수 있다.

### 4.2 식별자 매핑 조회
공급사 코드 → 내부 식별자, 내부 식별자 → 공급사 코드 양방향 조회를 제공한다.
검색 시 "보유 숙소 전체를 공급사별 코드로 묶는" 단계의 기반이다.
→ **구현: 검색에 필요한 방향만** — 공급사별 코드 목록과 (공급사, 숙소, 객실) → 내부 ID(`CatalogLookup`). 내부 ID → 공급사 코드 역방향은 검색이 쓰지 않아 만들지 않았고, 예약 대행(`09` §6)이 처음 필요로 한다.

### 4.3 통합 검색 (오케스트레이션)
날짜와 인원을 받아 검색 요청을 검증하고, 매핑에서 대상 숙소를 공급사별로 묶고, 어댑터를 병렬 호출하고, 결과를 병합해 표준 응답을 만든다.
공급사별 성공/실패를 추적하고 응답에 반영한다. 이 기능은 공급사 형식을 모른다.

### 4.4 공급사 어댑터 (A, B 각각)
공통 포트를 구현한다. WebClient로 자기 공급사를 호출하고, 응답을 역직렬화하고, 자기 공급사의 방식으로 실패를 판정해 공통 실패 타입으로 번역하고, 성공 응답을 표준 모델로 변환한다.
공급사별 DTO는 이 계층 밖으로 나가지 않는다. 타임아웃 설정을 소유한다.

### 4.5 요금 정규화
공급사별 요금 표현을 표준 요금 모델로 변환한다 (§3.2.2).
- 필수 계층 `price`: A는 `Σ(nightlyRate + taxAmount)`, B는 `totalPrice` 그대로. 통화·조식 포함 여부·숙박일수를 함께 담는다.
- 부가 계층 `priceDetail`: A만 채운다(세금 총액, 날짜별 내역). B는 `null`.
- A는 총액을 주지 않으므로 합계 검증은 성립하지 않는다(2026-09-05 정정). 항목 결함(음수 요금·세금, 통화 누락, 날짜 형식 오류)은
  그 항목만 제외하고 나머지는 살린다. 요청 기간 안의 날짜가 빠진 것은 결함이 아니라 재고 0 처리다(§3.6).
- 순수 함수로 유지한다 (외부 I/O·DB 접근 없음).

### 4.6 연박 재고 판정
요청 기간의 날짜별 잔여 객실 수로부터 "기간 전체를 예약할 수 있는 객실 수"를 계산한다.
최솟값 규칙, 누락 날짜 0 처리, 범위 밖 날짜 무시.

### 4.7 결과 병합 및 응답 구성
공급사별 정규화 결과를 하나의 목록으로 합치고, 실패한 공급사 목록과 조회 상태를 응답에 포함한다.
같은 숙소가 여러 공급사에서 오더라도 이 단계에서는 합치지 않고 각각 노출한다 (병합은 선택 구현).

### 4.8 실패 기록
공급사 호출 실패(타임아웃, 장애, 인증 실패 등)와 정규화 실패를 §3.7의 분류와 함께 기록한다.

**지표 수집은 설계로 미루지 않고 구현한다.** §3.7의 `SupplierResult`가 이미 공급사·API·결과 분류·소요시간을 들고 있으므로,
집계 지점을 한 곳(결과 병합 단계)에 두면 추가 비용이 거의 없다.

- 지표: `supplier.call` (Timer) — 태그 `supplier`, `api`(catalog|availability), `outcome`(success|timeout|supplier_error|auth_error|normalization_error)
  → **구현: `outcome`은 `success` + `FailureKind` 소문자 8종(9값).** 5값으로 접으면 429와 5xx가 합쳐져 동시성 상한의 근거(`RATE_LIMITED` 비율)를 잃는다(`08` §2).
  `Skipped`는 별도 Counter, 미매핑·격리는 `supplier.items.excluded{reason}`, 검색 상태는 `search.result{status}`
- 여기서 공급사별 **성공률·응답 지연 분포·타임아웃 비율**이 모두 파생된다
- Actuator로 노출해 README에 확인 방법을 적는다
- 정규화 실패·미매핑 상품(§3.5)도 같은 축으로 카운트한다

### 4.9 Mock 공급사 제어
Mock 서버의 응답 모드(정상/장애/무응답/지연)를 공급사별로 런타임에 전환한다.
통합 테스트와 수동 검증에서 견고성 동작을 재현하는 용도.

3. 어댑터 A·B — **실패 판정 통일(`SupplierResult`)을 이 단계에서 같이 만든다.** 나중에 붙이면 구조가 꼬인다

### Day 2 — 증명과 견고성

6. **통합 테스트로 견고성 증명** — "구현했다"가 아니라 테스트가 근거다 (§3.9)

9. 재시도 정책 · 서킷 브레이커 (라이브러리 도입이 막히면 설계 문서로 대체)

### Day 3 — 문서와 정리

10. **전체 코드 정독** — 설명할 수 없는 코드를 남기지 않는다 (리뷰에서 임의 지점을 짚어도 설명할 수 있어야 한다)

12. 커밋 히스토리 정리 — 고민의 과정이 드러나야 한다
13. 미구현 선택 항목의 **설계 문서** — 캐시 전략, 중복 병합을 하지 않은 이유, 예약 대행 흐름

### 시간이 부족하면 버리는 순서

9(재시도·서킷) → 8(청크) → 7(관측성) 순으로 버리고 **설계 문서로 대체**한다.
6(테스트)과 11(문서)은 버리지 않는다. 이 둘이 없으면 나머지를 만들었다는 근거가 사라진다.
